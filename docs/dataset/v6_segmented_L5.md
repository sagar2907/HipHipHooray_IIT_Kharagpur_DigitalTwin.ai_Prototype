## Why this exists

Two things landed the same day and point at the same fix:

1. `PROGRESS.md`'s own Workstream D gate says **"40 stations"** — L1–L4 top
   out at 30 (`LAYOUTS["L2"]`).
2. Priyansh's suggestion #8 and his Part A write-up (2026-08-25) argue that
   going from 20 to 40 stations isn't enough on its own — the three real
   segments (body/paint/final) behave differently, and **sensor coverage
   should vary by segment**, not be a uniform random draw.

Building "40 uniform stations" would have satisfied the letter of the gate
and missed the point of both. This satisfies both in one layout.

## Layout: L5, 40 stations = 15 body + 10 paint + 15 final

| Segment | Stations | Sigma (variance) | Sensor coverage | Vintage |
|---|---|---|---|---|
| Body | 15 | tight, 0.05–0.09 | ~90% instrumented (12% dark this build) | mostly modern (3 legacy) |
| Paint | 10 | wider, 0.10–0.16 | ~90% dark — 1 "booth" station carries a segment-level aggregate reading (obs=0.4) | mostly legacy (8 legacy) |
| Final | 15 | widest, CV-like 0.25–0.55 | ~65% dark (58% measured this build), rest covered by `manual_check` events | mostly modern (4 legacy) |

Vintage is a **fixed line property**, not drawn per-shift — matching how the
brief poses "layout, equipment vintage, and sensor maturity" as parallel
structural axes, not per-run random variables.

## What's new versus v5's schema

- **`manual_check.csv`** per run — `unit_id, station_id, check_id, result,
  reason_code, recorded_at_s, entry_latency_s, provenance`. Covers the 15
  final-assembly stations that are dark by design, not by dropout.
  Provenance is `attested` throughout — Part A's proposed fourth value
  alongside measured/inferred/predicted.
- **`coupling_map.csv`** per run — for every dark station, the nearest
  downstream non-dark station and hop count. **Simplification, stated
  plainly**: this is "nearest instrumented," not Part A 1.4's actual
  proposal of "nearest station with *measured* adequate detection power" —
  that needs a per-fault detectability study this script doesn't run.
- **`observability.csv`** gains `segment` and `vintage` columns, and a
  fourth coverage value (0.4, "booth-level only, not per-station") that
  didn't exist in v5's three-value scheme (dark/dropout/instrumented).
- **`run_manifest.csv`** gains `manual_check_stations`, `paint_booth_station`,
  `n_manual_checks`.

## Known limitations — stated here, not discovered later

- **Paint is NOT a true batch/oven resource.** The simulator is a per-unit
  serial-server architecture end to end; "capacity behaves differently from
  flow" is approximated with larger buffers ahead of paint stations (4–7
  vs the usual 1–3), so units cluster rather than draining one-for-one. A
  real shared-capacity batch mechanic needs new tick-loop logic in
  `plant.py`, and deliberately wasn't attempted here — new logic inside the
  CRN-preserving tick loop is exactly where this project's past bugs (RNG
  desync, unpaired counterfactuals) have come from, and this is a local
  draft, not something to risk the simulator's correctness on.
- **`manual_check`'s NOK rate (baseline 3.4%) and entry_latency are a
  first-pass model**, not fit to a real genealogy-vs-EOL cross-check —
  which is Part A 1.3's actual proposed validation and hasn't been run.
- **No truth labels.** `build_truth.py` generates sensitivity/regret/
  forecast labels generically over `LAYOUTS`, so it should work on L5
  without modification — but it's a ~2–3h job and wasn't run here to keep
  this a same-session deliverable. Flow data + manual_check + coupling map
  are ready now; economic ground truth is a follow-up step.
- **20 runs only** (2 per fault kind + 10 no-fault), single shift each —
  enough to validate the mechanism, not enough for a published number. v5's
  own L2/L3/L4 used a comparable density (5 faults + 7 no-fault = 12 runs
  each), so this isn't out of step with existing practice, but it's not the
  126-run depth L1 has either.

## Calibration references (external, real data — not invented numbers)

Researched and lightly downloaded for calibration, not merged into the
pipeline:

- **[Bosch Production Line Performance](https://www.kaggle.com/c/bosch-production-line-performance)**
  (Kaggle, 2016) — real automotive-adjacent line, **51 stations across 4
  lines**, defect rate **0.58%**. Used to sanity-check that 40 stations
  across 3 segments is a realistic scale, not an arbitrary number.
- **[AI4I 2020](https://archive.ics.uci.edu/dataset/601/ai4i+2020+predictive+maintenance+dataset)**
  (UCI, downloaded, 10,000 rows) — real machine-failure rate **3.39%**,
  named 5-mode taxonomy (TWF/HDF/PWF/OSF/RNF). `manual_check`'s baseline
  NOK rate (3.4%) is set from this, not picked arbitrarily.
- **[SECOM](https://archive.ics.uci.edu/ml/datasets/SECOM)** (UCI,
  downloaded, 1567×590) — real semiconductor sensor data: **4.54% overall
  missing rate, 116/590 (19.7%) near-constant/dead columns**. Used to check
  that v5's existing NULL-burst injection rate (35% of tools) is in a
  realistic band for how sparse real industrial sensor data actually gets —
  not changed here, just checked.

Raw downloads live in the session scratchpad, not this repo — they're
calibration references, not data this project ships.
