# v5 — the unified dataset

Generated by `scripts/build_v5.py` (flow + tools) and `scripts/build_truth.py`
(labels). Validate with `scripts/validate_v5.py`.

**This supersedes v3/flow, v4 and dataset/line entirely.** `dataset/v3/process`
is still current and complements this — see *Which dataset for which job* below.

## What makes v5 different: the tools live on the line

Until v5, tool telemetry and line events were separate universes — different
VINs, different stations, different clocks. That made the project's headline
claim untestable, because there was no way to join them.

The claim is the **joint stop-or-continue decision**: the same drifting tool
gets opposite correct answers depending on whether its station is currently the
constraint. If the station is *not* the constraint, stopping costs almost
nothing because buffers absorb it — fix it now. If it *is* the constraint,
every minute is a car, so wait for the next planned break.

In v5, each run's tool telemetry is generated from **that run's own vehicle
sequence and timestamps**. The join key `(run, station_id, vin)` is exact.
So this is now answerable:

> *Tool at S07 began drifting at t=10,240 s. Was S07 the constraint then?*

Validation confirms 100% VIN match between `tool_readings.csv` and
`unit_scan.csv` at the same station.

## Layout

```
dataset/v5/
  flow/
    run_manifest.csv            one row per run: config, fault, dark stations,
                                dropouts, tool stations, JPH, micro-stop count
    runs/<tag>/
      unit_scan.csv             OBSERVED  vin, station, in/out, t_s
      station_state.csv         OBSERVED  working/blocked/starved/down/break
      buffer_level.csv          OBSERVED  level, capacity, t_s
      tool_readings.csv         OBSERVED  torque, angle, current, temp, OK/NOK
      andon_log.csv             OBSERVED  operator stops with reason codes
      rework_log.csv            OBSERVED  EOL failures and repair returns
      calendar.csv              OBSERVED  breaks and lunch
      hidden/
        unit_scan_full.csv      includes dark stations
        station_state_full.csv  includes dark stations
        microstops.csv          every micro-stop: station, time, duration
        tool_truth.csv          condition, onset, true defects, escapes
        observability.csv       per-station: instrumented / dropout / dark
        artifacts.csv           every corruption we injected
        fault.json              injected fault truth
  truth/
    sensitivity.csv             per-block marginal-value vector + argmax
    sensitivity_raw.csv         per (run, block, station) gains
    persistence.csv             constraint episodes with mean margin
    forecast_labels.csv         h1/h2/h3 = 60/120/180 min horizons
    intervention.csv            paired-CRN outcomes of fix-now vs fix-at-break
```

**The hidden/ boundary is enforced by a test.** `validate_v5.py` checks that no
observed file carries a truth column. A model that reads `hidden/` is cheating.

## What each pipeline gets

### Pipeline 1 — bottleneck

Event logs give processing time, availability, blocked/starved shares, buffer
levels and slopes, variant sequence, break calendar. `truth/sensitivity.csv`
provides the **economic** ground truth — the station whose 30% speed-up
actually produces more cars, measured under common random numbers, averaged
over 4 replications, within 60-minute blocks.

**Read the no-fault runs correctly.** They have low margin, and that is not a
defect: a healthy balanced line genuinely has no single dominant bottleneck.
Measured, no-fault runs give top-station gain 7.0 and margin 3.8; faulted runs
give 18.0 and 12.0. Those are two different regimes and should be scored
separately. A detector that reports "no dominant constraint" on a healthy line
is *correct*, and the dataset lets you check that.

### Pipeline 2 — defect

972 tools on the line, and the three-way sensor/tool separation appears at
scale:

| condition | true defects | flagged NOK | escaped as OK | good parts rejected |
|---|---|---|---|---|
| sensor_bias | 7,483 | 152 | **7,339 (98%)** | 8 |
| pure_transducer_drift | 1 | 2,356 | 0 | **2,355** |
| gradual_wear | 5,180 | 5,180 | 0 | 0 |
| overtorque | 3,326 | 3,326 | 0 | 0 |
| lubrication_loss | 1,933 | 1,933 | 0 | 0 |
| spread_only | 1,727 | 1,727 | 0 | 0 |
| intermittent | 895 | 895 | 0 | 0 |
| healthy | 15 | 15 | 0 | 0 |

The two sensor faults have **opposite economics** — one hides real defects, the
other throws away good parts — and both look like "the torque reading moved."
That is the case for multi-channel monitoring plus mode classification.

### Pipeline 3 — dark stations

Three permanently dark stations per run (no scans, no states), two temporary
dropouts, and `observability.csv` grading every station.

**The bracketing confound is now measurable, not asserted.** On a sample dark
station, mean occupancy from boundary scans was **88.8 s** while true work time
was **58.0 s** — a 53% overstatement, because occupancy includes waiting caused
by neighbours. That is exactly why bracketing must be paired with a state
estimator rather than used alone.

Conveyor transit (2–6 s, lognormal) now exists, so the bracketing formula has a
real transit term to subtract — and it is a distribution, so its uncertainty can
be propagated.

## Measurement-layer artifacts

Applied to **observed files only**, after simulation, because they are
properties of the recording chain rather than the plant. Truth files stay clean.

| artifact | rate |
|---|---|
| per-controller clock skew | ±3 s, one offset per station |
| dropped scans | 0.2% |
| duplicated scans | 0.05% |
| late arrivals | 0.1%, delayed 30–180 s and delivered out of order |
| NULL bursts in tool channels | 35% of tools, 20–90 consecutive readings |
| temporary sensor dropout | 2 stations per run, 10–25% of the shift |

Clock skew is why **Tier B is "strongly estimated", not "exact"** — a bracketed
time inherits the skew of two different controllers. Claiming exactness while
injecting skew would contradict our own generator.

## Micro-stops

~97 per shift, 15–180 s each. Modelled as **inflated processing time with no
state change**, so they appear in **no** downtime log — validated: 2,648
micro-stops across 30 runs versus 876 logged `down` entries, with zero overlap.

They are recoverable only from anomalous dwell between two boundary scans,
which is the point: industry data puts minor stops at ~34% of production loss
and they are invisible in the plant's own reporting.

## Which dataset for which job

| Job | Use | Why |
|---|---|---|
| Bottleneck detection & forecasting | **v5/flow + v5/truth** | economic ground truth, 156 runs |
| Joint stop-or-continue decision | **v5** | only dataset where tools and flow share VINs |
| Dark-station methods | **v5** | transit time, clock skew, dropouts, consecutive dark blocks |
| Micro-stop detection | **v5** | only dataset containing them |
| Deep failure-mode classification | **v3/process** | 20,000 ops per tool vs ~300 on the line; 12 conditions; held-out and firewall sets |
| Held-out threshold calibration | **v3/process/holdout** | separate seed, all healthy |
| Generalisation check | **v3/process/firewall** | Wiener-process damage, never used in development |

v5's line-tools see only ~300 fastenings per station per shift, so their
degradation timescale is compressed to mature inside the run. For classifier
training use v3/process; use v5 to test the *decision* the classification feeds.

## Reproducing

```bash
python scripts/build_v5.py                    # flow + tools, ~3 min
python scripts/build_truth.py --workers 10    # sensitivity labels, ~2-3 h
python scripts/validate_v5.py                 # integrity + capability checks
```

Everything is seeded. `build_truth.py` checkpoints per run into
`truth/partial/`, so an interrupted build resumes rather than restarting.

## Known limitations

- Degradation timescales on line-tools are compressed; real tool wear takes days
- Transit time is lognormal around a per-station mean, not variant-dependent
- No operator effects (learning curve, absence, rotation)
- No changeover between product families, only variant mix within a family
- Sensitivity truth uses 30% perturbation; the marginal-value vector is
  therefore a finite-difference estimate, not a derivative
